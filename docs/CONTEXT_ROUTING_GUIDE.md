# Context Routing Guide

The Lisa Harness uses a declarative context admission system to determine how telemetry, operational alerts, and domain knowledge generated by extensions (Packs) are surfaced to the LLM.

Instead of hardcoding framework-level abstractions, the context mapper acts purely as a routing engine. It evaluates incoming `ContextItem` against the `context.sources` rules defined in your active session plan and renders matched candidates into ordered Markdown lanes.

## Why Context Routing?

1. **Reduce LLM Cognitive Load & Drift**: By strictly grouping related context into lanes and silencing healthy "green" telemetry, the LLM isn't distracted by ambient noise.
2. **Framework Agnosticism**: The kernel doesn't need to know anything about the context that packs provide or where/how it lives in the prompt.
3. **Customizable Prompt Architecture**: You control exactly what gets rendered and in what order.

---

## Configuration Location

Context routing rules are defined in the `context` block of your session context front matter (`session_context.md`). See the [Session Context Authoring Guide](SESSION_CONTEXT_AUTHORING_GUIDE.md) for the full schema.

```yaml
---
schema_version: 2
name: my-production-session
surface:
  type: personal_dm
  id: host-console
  memory_scope: personal
context:
  lanes:
    - lane_id: operational_state
      max_tokens: 1200
      render_order: 0
    - lane_id: financial_context
      max_tokens: 1000
      render_order: 10
    - lane_id: general_context
      max_tokens: 800
      render_order: 20
  sources:
    - rule_id: operational
      lane_id: operational_state
      evidence_types: [alert]
      sources: [cloudflare, github_actions]
    - rule_id: financial
      lane_id: financial_context
      tags: [billing, stripe]
    - rule_id: fallback
      lane_id: general_context
      fallback: true
---
```

## Configuration Schema

The `context` block is defined in [kernel/session_plan.py](../kernel/src/kernel/session_plan.py) as `ContextPlan`, `ContextLanePlan`, and `ContextSourceRule`.

### `context.lanes`

A list of named lanes, each with a `lane_id`, optional `min_tokens`/`max_tokens` budget, and a `render_order` that controls the top-to-bottom sequence in which lanes are injected into the final LLM prompt. Lane IDs must be unique.

### `context.sources`

A list of admission rules. Each rule has a unique `rule_id` and a `lane_id`
referencing a declared lane. **All populated selector fields must match**
(AND). Within a field, one listed value is enough; `tags` matches any
overlapping tag. Mode/stage, explicit-invocation, and freshness conditions
must also pass. For example, a rule with `sources: [stripe]` and
`evidence_types: [alert]` admits Stripe alerts, not all Stripe items or
every alert.

#### Match Selectors

* `sources`: Matches against `evidence.source` (e.g., `"cloudflare"`).
* `evidence_types`: Matches against `evidence.evidence_type` (e.g., `"alert"`).
* `tags`: Matches against items in `evidence.tags` (e.g., `"infrastructure"`).
* `packs`: Matches against the contributing pack name.
* `modes`: Matches against the active mode.
* `stages`: Matches against the active stage.
* `source_kinds`: Matches the normalized candidate kind (for example,
  `extension_item` or `state_item`), not the raw item's `source_type`.

*Note:* A rule needs at least one selector or `fallback: true`.

#### `fallback: true`

Designates a catch-all for candidates with no matching non-fallback source
selector. At most one fallback rule is allowed. A candidate whose source
selectors match but whose conditions fail is dropped; it does not bypass
the failed gate through fallback. Fallback candidates still obey admission
and budget rules.

#### `priority`

An integer (default `0`) used to select among matching source rules.
Higher priority wins. Equally preferred rules assigning one candidate to
different lanes are an explicit mapping error, not an arbitrary first match.

#### `required`

If `true`, matching candidates are selected before optional evidence, but
they must still fit the lane/global budget. If required content cannot fit,
the mapper raises `ContextBudgetError`; it never silently overfills the
window or drops required evidence.

`pinned` also prioritizes selection and bypasses diversity filtering, but
can be dropped when it cannot fit. It is not the same as `required`.

## Practical Examples

### Example 1: "Silence When Green" infrastructure monitoring

If you have operational packs loaded, you only want to distract the model when something is broken (alerts) or when the user explicitly queries about them.

```yaml
context:
  lanes:
    - lane_id: critical_alerts
      max_tokens: 1200
      render_order: 0
    - lane_id: ambient_telemetry
      max_tokens: 600
      render_order: 10
    - lane_id: general_context
      max_tokens: 800
      render_order: 20
  sources:
    - rule_id: alerts
      lane_id: critical_alerts
      evidence_types: [alert]
      priority: 100
    - rule_id: telemetry
      lane_id: ambient_telemetry
      sources: [cloudflare, azure_monitor, kubernetes]
    - rule_id: fallback
      lane_id: general_context
      fallback: true
```

*Tip:* Low `salience_score` lowers one ranking feature; it does not
automatically silence healthy telemetry. To enforce silence, omit healthy
items at the producer or author suitable source/condition gates such as
`evidence_types: [alert]` or `explicit_invocation: true`. Budgeted ranking
is not a guaranteed salience cutoff.

### Example 2: Domain-Specific Agent

If you are building an agent focused on resolving billing disputes, you might want billing data at the very top of the prompt to ensure maximum model attention.

```yaml
context:
  lanes:
    - lane_id: financial_ledger
      max_tokens: 1500
      render_order: 0
    - lane_id: communication_history
      max_tokens: 800
      render_order: 10
    - lane_id: general_context
      max_tokens: 600
      render_order: 20
  sources:
    - rule_id: ledger
      lane_id: financial_ledger
      sources: [stripe]
      tags: [invoice, refund]
      priority: 100
    - rule_id: comms
      lane_id: communication_history
      sources: [zendesk, gmail]
    - rule_id: fallback
      lane_id: general_context
      fallback: true
```

## Pack Authoring Interface (`ContextItem`)

If you are authoring a Lisa Pack, your pack simply yields `ContextItem` objects. You do not define where they go; you label them accurately so the end-user's `context.sources` rules can catch them. The mapper selects on `source`, `pack`, `source_type`, `evidence_type`, and `tags` — `namespace` is an author-facing provenance label only and is **not** a selection key.

```python
from kernel.models import ContextItem


def build_evidence() -> ContextItem:
    return ContextItem(
        item_id="stripe:customer_123",
        namespace="billing",  # Provenance label only — not a selector.
        source="stripe",  # -> Matched by sources: [stripe]
        source_type="extension",  # Normalized to source_kinds: [extension_item].
        evidence_type="status",  # -> Matched by evidence_types: [status]
        tags=["billing", "mrr"],  # -> Matched by tags: [billing, mrr]
        title="Customer Billing Status",
        body="MRR: $450 | Status: Past Due",
        salience_score=0.85,  # Ranking feature (0.0–1.0). Does NOT
        # guarantee inclusion — admission is
        # governed by source-rule priority /
        # required / pinned in the session plan.
        # The mapper recomputes relevance,
        # freshness, and recency each turn; only
        # salience_score is carried over.
    )
```

See [context lifecycle](CONTEXT_LIFECYCLE.md) for whole-request allocation,
resident tool-result references, replay, and caching. Lane admission is not
the complete model-request budget.
