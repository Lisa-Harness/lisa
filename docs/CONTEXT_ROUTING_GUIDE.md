# Context Routing Guide

The Lisa Framework uses a declarative Context Routing system to determine how telemetry, operational alerts, and domain knowledge generated by extensions (Packs) are surfaced to the LLM.

Instead of hardcoding framework-level abstractions (like "market signals" or "development state"), the Context Broker acts purely as a routing engine. It evaluates incoming `ContextEvidence` against the `context_routing` rules defined in your active session context and renders them into ordered Markdown namespaces.

## Why Context Routing?

1. **Reduce LLM Cognitive Load & Drift**: By strictly grouping related context into namespaces and silencing healthy "green" telemetry, the LLM isn't distracted by ambient noise.
2. **Framework Agnosticism**: The kernel doesn't need to know what "Cloudflare" or "Stripe" is. Packs emit evidence; your rules decide where it lives in the prompt.
3. **Customizable Prompt Architecture**: You control exactly what gets rendered and in what order.

---

## Configuration Location

Context routing rules are defined in the YAML front-matter of your `session_context.md` (or `session_context/` directories).

```yaml
---
name: my-production-session
context_routing:
  render_order:
    - operational_state
    - financial_context
    - general_context
  namespaces:
    operational_state:
      match_types: ["alert"]
      match_sources: ["cloudflare", "github_actions"]
    financial_context:
      match_tags: ["billing", "stripe"]
    general_context:
      is_fallback: true
---
```

---

## Configuration Schema

The `context_routing` block maps to the `ContextRoutingConfig` model.

### 1. `render_order`

A list of strings defining the top-to-bottom sequence in which namespaces are injected into the final LLM prompt. If omitted, the framework uses a sensible internal default, but it's highly recommended to explicitly declare your order if you are defining custom namespaces.

### 2. `namespaces`

A dictionary where the key is the name of the namespace (e.g., `operational_state`), and the value is a set of matching rules.

#### Match Rules

When the Context Broker evaluates an incoming piece of `ContextEvidence`, it checks the following arrays. If **any** condition matches, the evidence is assigned to that namespace.

* `match_sources`: Matches against `evidence.source` (e.g., `"cloudflare"`, `"dev_state"`).
* `match_types`: Matches against `evidence.evidence_type` (e.g., `"alert"`, `"recent_work"`).
* `match_tags`: Matches against items in `evidence.tags` (e.g., `"infrastructure"`, `"billing"`).

*Note: All matching is case-insensitive.*

#### `is_fallback: true`

Designates a namespace as the default catch-all. If a piece of evidence does not trigger any of the above match rules across *all* defined namespaces, it will be placed here. (If no fallback is defined, the framework defaults to `"general_context"`).

## Practical Examples

### Example 1: "Silence When Green" infrastructure monitoring

If you have operational packs loaded (like Cloudflare or AKS), you only want to distract the model when something is broken (alerts) or when the user explicitly queries about them.

```yaml
context_routing:
  render_order:
    - critical_alerts
    - ambient_telemetry
    - general_context
  namespaces:
    critical_alerts:
      # Only capture evidence specifically typed as an alert
      match_types: ["alert"]
    ambient_telemetry:
      # Capture status updates from known infra sources
      match_sources: ["cloudflare", "azure_monitor", "kubernetes"]
    general_context:
      is_fallback: true
```
*Tip: Packs should be written so their baseline `salience_score` is `0.0` when healthy. The Context Broker automatically drops evidence with low scores unless the user explicitly mentions the source in their query (lexical overlap).*

### Example 2: Domain-Specific Agent

If you are building an agent focused on resolving billing disputes, you might want billing data at the very top of the prompt to ensure maximum model attention.

```yaml
context_routing:
  render_order:
    - financial_ledger
    - communication_history
    - general_context
  namespaces:
    financial_ledger:
      match_sources: ["stripe", "sap"]
      match_tags: ["invoice", "refund"]
    communication_history:
      match_sources: ["zendesk", "gmail"]
    general_context:
      is_fallback: true
```

## Pack Authoring Interface (`ContextEvidence`)

If you are authoring a Lisa Pack, your pack simply yields `ContextEvidence` objects. You do not define where they go; you simply label them accurately so the end-user's routing config can catch them.

```python
from kernel.models import ContextEvidence

def build_evidence() -> ContextEvidence:
    return ContextEvidence(
        evidence_id="stripe:customer_123",
        source="stripe",           # -> Caught by match_sources
        evidence_type="status",    # -> Caught by match_types
        tags=["billing", "mrr"],   # -> Caught by match_tags
        title="Customer Billing Status",
        body="MRR: $450 | Status: Past Due",
        salience_score=0.85        # High salience (past due) guarantees inclusion
    )
```
