# Context Routing Guide

The Lisa Framework uses a declarative context admission system to determine how telemetry, operational alerts, and domain knowledge generated by extensions (Packs) are surfaced to the LLM.

Instead of hardcoding framework-level abstractions (like "market signals" or "development state"), the context mapper acts purely as a routing engine. It evaluates incoming `ContextEvidence` against the `context.sources` rules defined in your active session plan and renders matched candidates into ordered Markdown lanes.

## Why Context Routing?

1. **Reduce LLM Cognitive Load & Drift**: By strictly grouping related context into lanes and silencing healthy "green" telemetry, the LLM isn't distracted by ambient noise.
2. **Framework Agnosticism**: The kernel doesn't need to know what "Cloudflare" or "Stripe" is. Packs emit evidence; your rules decide where it lives in the prompt.
3. **Customizable Prompt Architecture**: You control exactly what gets rendered and in what order.

---

## Configuration Location

Context routing rules are defined in the `context` block of your session context front matter (`session_context.md`). See the [Session Context Authoring Guide](SESSION_CONTEXT_AUTHORING_GUIDE.md) for the full schema.

```yaml
---
schema_version: 2
name: my-production-session
surface:
  type: personal_dm
  id: host-console
  memory_scope: personal
context:
  lanes:
    - lane_id: operational_state
      max_tokens: 1200
      render_order: 0
    - lane_id: financial_context
      max_tokens: 1000
      render_order: 10
    - lane_id: general_context
      max_tokens: 800
      render_order: 20
  sources:
    - rule_id: operational
      lane_id: operational_state
      evidence_types: [alert]
      sources: [cloudflare, github_actions]
    - rule_id: financial
      lane_id: financial_context
      tags: [billing, stripe]
    - rule_id: fallback
      lane_id: general_context
      fallback: true
---
```

## Configuration Schema

The `context` block is defined in [kernel/session_plan.py](../kernel/session_plan.py) as `ContextPlan`, `ContextLanePlan`, and `ContextSourceRule`.

### `context.lanes`

A list of named lanes, each with a `lane_id`, optional `min_tokens`/`max_tokens` budget, and a `render_order` that controls the top-to-bottom sequence in which lanes are injected into the final LLM prompt. Lane IDs must be unique.

### `context.sources`

A list of admission rules. Each rule has a `rule_id` (must be unique) and a `lane_id` (must reference a declared lane). When the context mapper evaluates an incoming piece of `ContextEvidence`, it checks the rule's selectors. If **any** selector matches, the evidence is assigned to that rule's lane.

#### Match Selectors

* `sources`: Matches against `evidence.source` (e.g., `"cloudflare"`, `"dev_state"`).
* `evidence_types`: Matches against `evidence.evidence_type` (e.g., `"alert"`, `"recent_work"`).
* `tags`: Matches against items in `evidence.tags` (e.g., `"infrastructure"`, `"billing"`).
* `packs`: Matches against the contributing pack name.
* `modes`: Matches against the active mode.
* `stages`: Matches against the active stage.
* `source_kinds`: Matches against the candidate source kind.

*Note: A rule needs at least one selector or `fallback: true`. At most one fallback rule is allowed.*

#### `fallback: true`

Designates a rule as the default catch-all. If a piece of evidence does not trigger any other rule, it will be assigned to this rule's lane. At most one fallback rule is allowed across all sources.

#### `priority`

An integer (default `0`) that controls admission priority when multiple rules match the same candidate. Higher priority wins.

#### `required`

If `true`, matching candidates are always admitted if they match, regardless of budget pressure.

## Practical Examples

### Example 1: "Silence When Green" infrastructure monitoring

If you have operational packs loaded (like Cloudflare or AKS), you only want to distract the model when something is broken (alerts) or when the user explicitly queries about them.

```yaml
context:
  lanes:
    - lane_id: critical_alerts
      max_tokens: 1200
      render_order: 0
    - lane_id: ambient_telemetry
      max_tokens: 600
      render_order: 10
    - lane_id: general_context
      max_tokens: 800
      render_order: 20
  sources:
    - rule_id: alerts
      lane_id: critical_alerts
      evidence_types: [alert]
      priority: 100
    - rule_id: telemetry
      lane_id: ambient_telemetry
      sources: [cloudflare, azure_monitor, kubernetes]
    - rule_id: fallback
      lane_id: general_context
      fallback: true
```

*Tip: Packs should be written so their baseline `salience_score` is `0.0` when healthy. The context mapper automatically drops evidence with low scores unless the user explicitly mentions the source in their query (lexical overlap).*

### Example 2: Domain-Specific Agent

If you are building an agent focused on resolving billing disputes, you might want billing data at the very top of the prompt to ensure maximum model attention.

```yaml
context:
  lanes:
    - lane_id: financial_ledger
      max_tokens: 1500
      render_order: 0
    - lane_id: communication_history
      max_tokens: 800
      render_order: 10
    - lane_id: general_context
      max_tokens: 600
      render_order: 20
  sources:
    - rule_id: ledger
      lane_id: financial_ledger
      sources: [stripe, sap]
      tags: [invoice, refund]
      priority: 100
    - rule_id: comms
      lane_id: communication_history
      sources: [zendesk, gmail]
    - rule_id: fallback
      lane_id: general_context
      fallback: true
```

## Pack Authoring Interface (`ContextEvidence`)

If you are authoring a Lisa Pack, your pack simply yields `ContextEvidence` objects. You do not define where they go; you simply label them accurately so the end-user's routing config can catch them.

```python
from kernel.models import ContextEvidence

def build_evidence() -> ContextEvidence:
    return ContextEvidence(
        evidence_id="stripe:customer_123",
        source="stripe",           # -> Caught by match_sources
        evidence_type="status",    # -> Caught by match_types
        tags=["billing", "mrr"],   # -> Caught by match_tags
        title="Customer Billing Status",
        body="MRR: $450 | Status: Past Due",
        salience_score=0.85        # High salience (past due) guarantees inclusion
    )
```
