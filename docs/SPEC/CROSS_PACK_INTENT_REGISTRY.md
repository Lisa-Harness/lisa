# SPEC: Cross-Pack Intent Registry

Status: Draft for implementation by the `lisa-packs` coding agent
Author: Adam (with Lisa)
Date: 2026-07-27
Target repos: `lisa` (kernel + SDK core), `lisa-packs` (packs), `lisa-packs-wip` (WIP packs, optional scan target)

---

## 1. Problem

Lisa cannot tell a user that a missing capability exists in an uninstalled pack. Intent detection in `kernel/turn_phases/_routing_hint.py:_detect_query_intents` is **install-gated**: it only attributes an intent by matching an *installed* routing target's `routing_intent_keywords` / `fast_path_patterns`. When a pack is not installed, its keywords are absent from every routing target, so the intent is never detected, no routing hint fires, and the model answers in `default` mode with whatever tools it has — never mentioning the gap.

Today there is no machine-readable catalogue of "packs that exist but are not installed." The framework only knows what `importlib.metadata.entry_points(group="lisa.extensions.content_roots")` exposes, i.e. installed packs. A user asking "write a markdown report" with `lisa-pack-markdown` uninstalled gets a silent, wrong, in-`default` attempt instead of "install `lisa-pack-markdown`."

## 2. Goal

Build a **deterministic, sub-second scan** that harvests the intent vocabulary from every pack in the `lisa-packs` (and optionally `lisa-packs-wip`) repository roots, regardless of install state, and exposes it to the kernel so that:

1. The routing hint and `plan_workflow` can detect "uninstalled intent" — a query whose keywords match a pack that is not currently installed — and surface an actionable "install `lisa-pack-X`" message to the user.
2. The intent→pack mapping is durable enough that Lisa can later **auto-install on demand** (with user confirmation in the first phase; unattended in a later phase).

## 3. Non-goals

- Auto-installing without explicit user approval in phase 1. The registry only *suggests*; the user runs `/pack install`.
- A remote registry / network calls. The scan is local-filesystem only. Packs not cloned into `lisa-packs*` are invisible (acceptable; the WIP repos close most of the gap).
- Changing the existing `_mode.md` front-matter schema. The scanner reads existing fields; it does not redefine them.
- A new intent-tag vocabulary owned by the kernel. Intent tags stay pack-authored and opaque (existing tag-blind contract).

## 4. Existing assets to reuse

- **OKF v0.2** (`lisa-packs/okf`) — vendor-neutral markdown-with-YAML-frontmatter bundle format. Has `okf_validate`, `okf_ingest`, `okf_emit_concept` operations. Concept `type` is the only required field. The registry output is an OKF bundle — see §6.
- **`_mode.md` front matter** — every pack mode already declares `mode_id`, `mode_provider_id`, `routing_intent_tags`, `routing_intent_keywords`, `fast_path_patterns`, `command_pattern`, `satisfies_intents`, `description`. The scanner parses these fields; it does not invent new ones.
- **`pyproject.toml` entry point** `lisa.extensions.content_roots` — already maps a pack to its `get_content_root()` loader. The scanner reads `pyproject.toml` to get the canonical pack name (`[project].name`, e.g. `lisa-pack-search`) and the content-root loader.
- **`pack_autoinstall.py`** + **`_packs.run_pack_install_sync`** — already know how to install a pack from a local path or git ref, honour `LISA_PACK_ALLOWED_PREFIXES`, `LISA_PACK_GIT_ROOT`, `LISA_PACK_GIT_ALLOW_HOSTS`, and pin git refs. The registry feeds this machinery; it does not replace it.
- **`PackInstallSpec`** (`kernel.session_plan`) — `{source, pin, editable}` install descriptor. The registry's per-pack install descriptor reuses this shape.
- **`pack_allowed_prefixes()`** (`_packs.py`) — the trust policy the install path enforces. The registry's install suggestion is already policy-conformant by construction (pack names start with `lisa-pack-`).

## 5. The Intent Registry Bundle (OKF)

The registry is itself an **OKF v0.2 bundle** stored at a stable path (default `artifacts/intent-registry/`). It is regenerated by a scan; it is not hand-edited. It MUST pass `okf_validate`.

### 5.1 Bundle layout

```text
artifacts/intent-registry/
├── index.md                       # OKF index: pack count, scan time, source roots
├── log.md                         # OKF log: append-only scan history
├── packs/
│   ├── lisa-pack-search.md        # one concept per known pack
│   ├── lisa-pack-markdown.md
│   ├── lisa-pack-coding.md
│   └── ...
└── intents/
│   ├── research.md                # one concept per known intent tag
│   ├── write.md
│   ├── coding.md
    └── ...
```

### 5.2 Pack concept front matter (type: `Lisa Pack`)

```yaml
---
type: Lisa Pack
title: lisa-pack-search
description: Web search and reasoning pack
tags: [pack, search, research]
generated: { by: intent-registry-scanner, at: 2026-07-27T17:11:00Z }
status: stable
pack_name: lisa-pack-search              # canonical pyproject [project].name
pack_version: 0.1.0                      # pyproject [project].version
source_root: C:\Code\lisa-packs\search   # absolute path at scan time
content_root_entrypoint: search          # lisa.extensions.content_roots entry name
install:
  source: C:\Code\lisa-packs\search      # a PackInstallSpec.source value
  editable: true
  pin: ""                                # git ref pin, empty for local paths
modes:                                   # every routable mode this pack declares
  - mode_id: search
    routing_intent_tags: [research]
    satisfies_intents: [research]
    priority: 7
    command_pattern: "^(?:/)?search[\\s,:;]+(?P<query>.+)$"
  - mode_id: ponder
    routing_intent_tags: [research, reasoning]
    satisfies_intents: [research, reasoning]
    priority: 8
intents: [research, reasoning]           # flat union of routing_intent_tags across this pack's modes
---
```

### 5.3 Intent concept front matter (type: `Lisa Intent`)

```yaml
---
type: Lisa Intent
title: research
description: Web search and synthesis of current information
tags: [intent, research]
generated: { by: intent-registry-scanner, at: 2026-07-27T17:11:00Z }
status: stable
intent_tag: research                     # opaque pack-authored string (kernel does not interpret)
provided_by_packs: [lisa-pack-search]     # packs whose modes declare this in routing_intent_tags
keywords:                                # union of routing_intent_keywords[intent] across providing packs
  - search
  - latest
  - recent
  - current
  - news
  - update
  - today
fast_path_patterns:                      # union of fast_path_patterns from modes whose routing_intent_tags include this intent
  - "^(?:search(?:\\s+the\\s+web)?|web\\s+search|look\\s+up|find\\s+(?:recent|latest|current))\\b"
---
```

### 5.4 OKF conformance

- Every `.md` file under `packs/` and `intents/` MUST have parseable YAML front matter with a non-empty `type` (`Lisa Pack` or `Lisa Intent`). The scanner runs `okf_validate` on its own output before exposing the bundle; a non-conformant bundle is a scanner bug, not a runtime concern.
- `index.md` and `log.md` are reserved OKF filenames. `index.md` lists pack/intent counts and the source roots scanned; `log.md` appends one line per scan (`2026-07-27T17:11Z scan roots=lisa-packs,lisa-packs-wip packs=8 intents=6`).

## 6. The Scanner

A new operation `intent_registry_scan` lives in a new pack `lisa-pack-intent-registry` (under `lisa-packs/`), so the feature is itself pack-delivered and uninstallable. It is a no-LLM deterministic operation, mirroring `okf_validate`.

### 6.1 Parameters

```python
class Parameters(BaseModel):
    source_roots: list[str] = Field(
        default_factory=lambda: _default_roots(),
        description="Absolute paths to scan. Defaults to LISA_PACKS_ROOTS env or [lisa-packs].",
    )
    include_wip: bool = Field(
        default=False,
        description="Also scan lisa-packs-wip when present.",
    )
    output_bundle: str = Field(
        default="artifacts/intent-registry",
        description="OKF bundle directory to write.",
    )
    skip_build_dirs: bool = Field(
        default=True,
        description="Skip any path containing a build/ segment (stale dist artifacts).",
    )
```

`_default_roots()` reads `LISA_PACKS_ROOTS` (comma-separated absolute paths). When unset, it uses the repository-relative `..\lisa-packs` (and `..\lisa-packs-wip` when `include_wip=True`).

### 6.2 Algorithm

For each `source_root`, for each immediate child directory `pack_dir`:

1. Skip if `skip_build_dirs` and `build/` exists in the path segment chain (the editable install points at `lisa_packs/`, not `build/lib/`).
2. Read `pack_dir/pyproject.toml`. Skip if absent or has no `[project].name` starting with an entry in `pack_allowed_prefixes()` (default `lisa-pack-`).
3. Read `pack_dir/pyproject.toml`'s `[project.entry-points."lisa.extensions.content_roots"]` to get the content-root entry name and loader. Skip if absent (the pack is not a content pack).
4. Walk `pack_dir/**/modes/**/_mode.md` (recursive). For each file, parse YAML front matter via `kernel.ipsar_fsm.parse_front_matter`.
5. For each mode with `routable: true`, collect:
   - `mode_id`, `mode_provider_id`, `routing_intent_tags`, `satisfies_intents`, `priority`, `command_pattern`, `description`.
6. Accumulate per-pack `intents` = union of `routing_intent_tags` across its routable modes. Accumulate per-intent `provided_by_packs`, `keywords`, `fast_path_patterns` across all packs.
7. Build the OKF bundle:
   - Write one `packs/<pack_name>.md` per pack via `okf_emit_concept`'s `format_okf_frontmatter` helper (reuse, do not duplicate the writer).
   - Write one `intents/<intent_tag>.md` per intent.
   - Write/append `index.md` and `log.md`.
8. Run `okf_validate` on the output bundle. On failure, raise `OperationResult(output_text="intent-registry bundle non-conformant: <report>")` — never expose a broken bundle.

### 6.3 Performance budget

- Sub-second for the current 6 + 5 packs. The scanner does no model calls, no network, no `pip install`. It reads `pyproject.toml` + a handful of small markdown files per pack. Target: <500 ms cold.
- Re-scan is idempotent: overwriting `packs/*.md` and `intents/*.md` with fresh content is safe; `log.md` is append-only.
- The host boot path loads the bundle once via `okf_ingest` (also no model calls) and caches the parsed structure in memory.

### 6.4 Command surface

- `/intent-registry scan` (or `/intent-registry scan --include-wip`) — runs the operation. Requires restart to reload the in-memory registry.
- `/intent-registry show` — prints the current in-memory registry: pack count, intent count, and per-intent providing packs.
- `/intent-registry status` — last scan time, source roots, bundle path, conformant yes/no.

## 6.5 Host-layer bootstrap bridge (the registry is itself uninstalled)

**Layering rule:** the kernel stays registry-agnostic. The kernel's `_detect_uninstalled_intents` (§7.2) only fires when a registry is *loaded*; it never knows the registry pack exists. The **host** owns the bootstrap problem: "the registry itself is an uninstalled pack, so who tells the user to install the registry?" This is a host-layer concern because it depends on `importlib.metadata` (installed-pack introspection) and on host-owned restart/install machinery — neither belongs in the kernel.

### 6.5.1 The two failure modes the bridge distinguishes

| State | `lisa-pack-intent-registry` | `IntentRegistry` loaded | User sees |
| --- | --- | --- | --- |
| A | not installed | no | host bridge message: "install `lisa-pack-intent-registry` to enable missing-capability hints (or let me install it)" |
| B | installed but no bundle scanned | yes (empty) | host bridge message: "run `/intent-registry scan` (or let me) to build the catalogue" |
| C | installed + bundle loaded | yes (populated) | kernel routing hint names the specific missing pack (§7.3) — bridge silent |

The bridge handles A and B. State C is the kernel's job and the bridge is silent.

### 6.5.2 Where the bridge lives

A new host module `hosts/core/intent_registry_bridge.py` (mirrors `hosts/core/pack_autoinstall.py`: synchronous, host-owned, no kernel imports beyond the registry loader's public type). It exposes:

```python
def registry_pack_is_installed() -> bool:
    """True when importlib.metadata sees the lisa-pack-intent-registry
    entry point. Install-gated by construction — same mechanism as
    pack_autoinstall._installed_pack_names."""

def registry_bundle_is_loaded(runtime: HostRuntime) -> bool:
    """True when runtime.intent_registry is non-None and non-empty.
    The host sets runtime.intent_registry during _initialize_runtime
    (see 6.5.3); the kernel never reads this attribute."""

def maybe_install_registry_pack(runtime: HostRuntime) -> bool:
    """Install lisa-pack-intent-registry from the configured source and
    request a restart. Returns False (no-op) when:
      - the pack is already installed, OR
      - the session plan disables auto-install of the registry
        (resources.packs.auto_install_intent_registry: false, default true),
      OR
      - the user has dismissed the bridge prompt this session
        (runtime.intent_registry_bridge_dismissed).
    Reuses run_pack_install_sync + the existing trust policy
    (LISA_PACK_ALLOWED_PREFIXES already permits lisa-pack-*)."""
```

### 6.5.3 Boot wiring

In the host's `_initialize_runtime`, after `pack_autoinstall.auto_install_required_packs` and before content-root discovery:

1. `runtime.intent_registry = None` (typed `IntentRegistry | None`, host-owned attribute; the kernel never reads it).
2. If `registry_pack_is_installed()`:
   - Load the bundle from `artifacts/intent-registry/index.md` via the registry loader (§7.1).
   - If the bundle is absent or fails `okf_validate`, `runtime.intent_registry` stays `None` (state B — bridge will offer the scan).
   - Else `runtime.intent_registry = loaded` (state C — bridge silent).
3. Else: `runtime.intent_registry = None` (state A — bridge will offer the install).

The registry pack's `required` status is **not** forced. Adding it to `resources.packs.required` would auto-install it at boot (existing `pack_autoinstall` behaviour) — that's the zero-config path for users who want it, but it stays opt-in via the session plan. The bridge is the path for users who did not opt in.

### 6.5.4 The bridge prompt — host-injected, not model-generated

The bridge message is **deterministic host text**, not model prose. It is injected as a host-owned system-prompt fragment via the existing `assemble_system_prompt` path (the same seam that injects `copilot_customizations_text` in `hosts/core/turn_hooks_builder._assemble_system_prompt`). Rationale: the model has no way to know the registry exists (it's not installed), so asking it to generate the message would hallucinate. The host knows and the host writes the line.

The fragment is short and appended only when the bridge is active:

**State A** (registry not installed):

```markdown
## Missing Capability Hint

No capability catalogue is installed. Lisa cannot tell you which pack to add
when a request needs an uninstalled capability. Install the catalogue pack
to enable this: run `/pack install lisa-pack-intent-registry`, or say
"install the intent registry" and Lisa will install it for you, then restart.
```

**State B** (registry installed, no bundle):

```markdown
## Missing Capability Hint

The capability catalogue is installed but not populated. Run
`/intent-registry scan` to scan available packs, or say "scan for packs"
and Lisa will run it. Until then Lisa cannot suggest packs for uninstalled
capabilities.
```

**State C**: no fragment (silent — the kernel's §7.3 hint takes over).

### 6.5.5 "Install the intent registry" / "scan for packs" — host command interception

The user's natural-language reply ("install the intent registry", "scan for packs") is intercepted by the **host** before the turn reaches the kernel, mirroring how `/pack` and `/deep` are host-reserved commands (see `hosts/cli/repl.py` line 74 — `/pack install` is already a REPL completion). The host adds two natural-language triggers to its command interception layer:

- `r"^(?:install|add|get)\b.*\bintent[\s-]?registry\b"` → `maybe_install_registry_pack(runtime)` (state A → install + restart).
- `r"^(?:scan|build|refresh)\b.*\bpacks?\b"` (only when in state B) → invoke the `intent_registry_scan` operation via the host's `_execute_operation` seam, then reload `runtime.intent_registry`, then continue the turn with the now-populated registry.

These never reach the kernel. They are host command dispatch, not routing.

### 6.5.6 Dismissal and "don't show again"

`runtime.intent_registry_bridge_dismissed: bool` (host runtime state, not persisted across sessions by default). Set when the user says "dismiss", "not now", or explicitly runs `/pack install lisa-pack-intent-registry` themselves. The bridge fragment is suppressed while dismissed. A fresh session re-offers once (state A or B), so the hint is not permanently lost — but it does not nag within a session.

### 6.5.7 Phase mapping

- **Phase 1 (this SPEC):** the bridge implements state A's *suggestion* ("run `/pack install lisa-pack-intent-registry`") and state B's *suggestion* ("run `/intent-registry scan`"). The "install it for you" wording in §6.5.4 is a phase-2 affordance; in phase 1 the fragment reads "run `/pack install ...`" only.
- **Phase 2:** the natural-language triggers in §6.5.5 perform the install/scan and restart/reload automatically (the "or say 'install the intent registry' and Lisa will install it for you" path). This is the same `confirm` gate as §9 phase 2 — the registry install is just the first instance of it.

## 7. Kernel integration

### 7.1 Registry loader

A new in-memory structure in the kernel:

```python
@dataclass(frozen=True)
class IntentRegistryEntry:
    intent_tag: str
    provided_by_packs: tuple[str, ...]   # canonical pack names
    keywords: tuple[str, ...]            # lowercased
    fast_path_patterns: tuple[str, ...] # compiled regex cache

@dataclass(frozen=True)
class IntentRegistry:
    intents: Mapping[str, IntentRegistryEntry]
    packs: Mapping[str, PackRegistryEntry]   # by canonical pack name
    scanned_at: str
    source_roots: tuple[str, ...]
```

Loaded by a host boot hook (mirror `pack_autoinstall.auto_install_required_packs`): if `artifacts/intent-registry/index.md` exists and passes `okf_validate`, ingest it; else the registry is empty and the framework degrades to today's install-gated behaviour. **The registry is optional.** A missing or stale registry never blocks startup.

### 7.2 Pre-detection pass (the core behavioural change)

In `kernel/turn_phases/_routing_hint.py`, add a new function `_detect_uninstalled_intents` that runs **before** the existing `_detect_query_intents`:

```python
def _detect_uninstalled_intents(
    *,
    query: str,
    installed_pack_names: set[str],
    registry: IntentRegistry | None,
) -> list[UninstalledIntent]:
    """Return intents the query expresses that no installed pack provides."""
```

Logic:

1. If `registry is None`, return `[]` (today's behaviour).
2. For each `IntentRegistryEntry`, if any of its `keywords` (substring) or `fast_path_patterns` (regex) match the lowercased query, the query *expresses* that intent.
3. If none of `entry.provided_by_packs` is in `installed_pack_names`, the intent is **uninstalled**. Add it to the result with the providing pack names.
4. Return the list. Tag-blind: the kernel quotes `intent_tag` and pack names verbatim; it does not interpret them.

### 7.3 Hint integration

In `_compute_capability_routing_hint`, after computing the install-gated `detected_intents` (unchanged), call `_detect_uninstalled_intents`. When the result is non-empty, emit a **dedicated hint** that takes precedence over the existing Section 6 fallback:

```markdown
## Routing Hint — Missing Capability

No installed pack provides the `write` capability this request needs.
Install one of: `lisa-pack-markdown` (run `/pack install lisa-pack-markdown`).
Then re-run your request.
Do NOT attempt this with the current mode's tools.
```

This is the only place the kernel names pack names — and only because the registry (a pack-authored data structure) told it to, preserving tag-blindness.

### 7.4 `plan_workflow` integration

In `sdk/packs/core/operations/planning/plan_workflow.py`, before the model call, run `_detect_uninstalled_intents`. When non-empty, return an empty `target_stage_id` with a rationale that names the missing capability and the install command — reusing the rationale contract already tightened in commit `0b76759`.

## 8. Intent → pack mapping (for auto-install)

The registry's `IntentRegistryEntry.provided_by_packs` is the mapping. When multiple packs provide the same intent (e.g. two search packs), the mapping is a **list**, and selection is by:

1. **Already-installed wins** — if any provider is installed, the intent is not "uninstalled" and the existing routing handles it.
2. **Priority** — when suggesting an install, prefer the provider whose mode has the highest `priority` (lowest number = highest priority, matching existing mode precedence).
3. **Session plan `auto_install`** — if the session context declares an `auto_install` source for one of the providers, that one wins.
4. **First by name** — deterministic tiebreak for the suggest-only phase.

This mapping is the contract that enables phase-2 auto-install: the host already has `run_pack_install_sync` + `PackInstallSpec`; the registry supplies the `source` (the local `source_root` from the scan, or a git ref from a future remote field). Auto-install is gated behind a session-plan flag (see §10) and a user confirmation in phase 1.

## 9. Phases

### Phase 1 — Suggest (this SPEC, implementable now)

- `lisa-pack-intent-registry` pack with the `intent_registry_scan` operation.
- Kernel `IntentRegistry` loader + `_detect_uninstalled_intents`.
- Routing hint + `plan_workflow` empty-target rationale surface "install `lisa-pack-X`."
- `/intent-registry scan|show|status` commands.
- No automatic install. The user runs `/pack install <suggested>` themselves.

### Phase 2 — Confirm-then-install (later, smaller change)

- A new session-plan key `routing.auto_install_missing: true` (default `false`).
- When the hint fires AND the flag is set, the host prompts the user once per missing intent per session: "Install `lisa-pack-markdown` to handle `write`? [y/N]". On `y`, call `run_pack_install_sync` with the registry's `PackInstallSpec`, then `request_restart`.
- Reuses all existing trust policy (`LISA_PACK_ALLOWED_PREFIXES`, etc.) — no new trust surface.

### Phase 3 — Unattended auto-install (later still)

- Session-plan flag `routing.auto_install_missing: unattended`.
- Honour the existing `LISA_PACK_REQUIRE_GIT_REF` pin rule; local-path sources from the scan are already editable.
- Audit log entry per auto-install in `artifacts/intent-registry/log.md`.

## 10. Session plan schema additions (phase 2/3 only)

```yaml
routing:
  start_mode: default
  auto_install_missing: false   # phase 2; or `unattended` in phase 3
```

`compile_session_plan` adds the field with a strict `Literal["off", "confirm", "unattended"]` (default `"off"`). No schema change in phase 1 — the registry is loaded opportunistically and the hint fires regardless.

## 11. Edge cases & contract

- **Pack installed but stale**: the registry is a catalogue of *known* packs, not a freshness check. If `lisa-pack-search` is installed, the intent is "installed" regardless of version drift. Version pinning is the install path's job.
- **Two packs provide the same intent**: §8 selection. The hint lists all providers; the user picks.
- **Pack in WIP not yet installable**: when `include_wip=False` (default), WIP-only packs are not in the registry, so they are never suggested. When `include_wip=True`, they appear but their `install.source` is the WIP local path (editable). The scanner does not distinguish "released" from "WIP"; the user controls this via the scan flag.
- **Registry absent or non-conformant**: framework degrades to today's install-gated behaviour. No hard dependency on the registry existing.
- **Keyword collision across intents**: an intent is "uninstalled" only if *no* provider is installed. If installed pack A's keywords also match a query that uninstalled pack B would handle better, the existing routing-hint logic (gap after `satisfies_intents`) already handles A's gap. The registry only adds the "nobody installed" case.
- **Trust policy**: the scanner reads `pack_allowed_prefixes()` so it never catalogues a pack the install path would reject. The install suggestion is policy-conformant by construction.

- [ ] `operations/registry/intent_registry_scan.{py,yml}` — the no-LLM deterministic scanner (§6). Parameters per §6.1, algorithm per §6.2.

- [ ] `commands.py` — `/intent-registry scan|show|status` (§6.4). `scan` invokes the operation; `show` prints the in-memory registry; `status` reports last-scan time / source roots / conformant yes/no.
- [ ] Pack concept writes use `type: Lisa Pack`; intent concept writes use `type: Lisa Intent` (§5.2–§5.3). The scanner is the only writer of these; the kernel only reads.
- [ ] Tests: scanner produces a conformant bundle from a fixture pack tree (two fake packs with two `_mode.md` files each); the output passes `okf_validate`; re-scan is idempotent; `skip_build_dirs` skips `build/lib/`; a pack without the `lisa.extensions.content_roots` entry point is skipped; a pack whose name fails `pack_allowed_prefixes()` is skipped.

### 12.3 Integration & contract seam

- [ ] **Contract test** (lives in the `lisa` repo, gated on the pack being installed): scan a fixture pack tree via the pack's operation, load the resulting bundle via `kernel.intent_registry.load_intent_registry`, and assert `_detect_uninstalled_intents` returns the expected uninstalled intent. This is the only test that needs both repos; it is skipped when `lisa-pack-intent-registry` is not importable.
- [ ] **Schema pin**: the OKF concept `type` strings (`Lisa Pack`, `Lisa Intent`) and the front-matter keys in §5.2–§5.3 are the inter-repo contract. Either side changing them is a coordinated change, not an independent one. The kernel's `load_intent_registry` MUST fail loudly (raise, not silently degrade) on a bundle whose concepts have unknown `type` values — that's the version-drift detector.

## 13. Out of scope, explicitly

- Network/remote pack registry. Local scan only.
- Renaming or re-versioning OKF. The registry reuses OKF v0.2 as-is.
- New kernel-owned intent vocabulary. Tags stay pack-authored.
- Phase 2/3 auto-install machinery (only the mapping contract is fixed here so phase 2 is a small change).
- Scanning non-`lisa-packs` locations (user pack dirs). Configurable via `LISA_PACKS_ROOTS` env, but no UI for arbitrary paths in phase 1.
