# November Roadmap — Observability & Replay Program

*This roadmap, dated 2026-11-13, is a durable planning document. It classifies specs, sequences work, and names immediate actions.*

## 1. Purpose and how to read this

The specs in `docs/SPEC/` were written or refreshed on 2026-11-13/14 and define the next body of work. This roadmap classifies every spec in that folder by status and repository ownership, sequences the work, and names the immediate next action. The classification rule is: a spec is either (a) active work for this repo, (b) completed work for this repo, (c) aspirational/deferred, or (d) owned by another repository and only tracked here.

## 2. The four-spec build program (specs 1–4) — ACTIVE, this repo

These four were explicitly defined to be implemented, in this dependency order. They form a numbered program with a strict dependency chain: Spec 1 unblocks 2, 3, and 4; Spec 2 depends on Spec 1 and unblocks Spec 3; Spec 3 depends on Specs 1 and 2; Spec 4 depends on Spec 1 but can start in parallel with 2 and 3. For each spec below, the goal, concrete modules/files touched, key data shapes introduced, and acceptance gate are given.

### Spec 1 — Evidence Envelope (docs/SPEC/EVIDENCE-ENVELOPE.md), Order 1 of 4, depends on nothing, unblocks 2, 3, 4

**Goal:** Make every durable evidence row self-describing, versioned, and addressable to the exact model call, dispatch, run configuration, and parent turn that produced it. Today ledgers join only at turn granularity (`turn_index`, `user_slug`, `thread_store_slug`), so a turn with several iterations cannot attribute cost to the request that incurred it.

**Concrete content:**

- A common envelope on every ledger row: `topic`, `schema_version`, `emitted_at`, `logged_at`, `sequence`, `ledger_instance`, `user_slug`, `thread_store_slug`, `turn_index`, `turn_id`, `run_ref`, and reserved `trace_id`/`span_id` (null until Spec 4). Handler-stamped fields are written by the ledger handler, never by publishers.
- Typed per-topic payload models in the kernel with write-time allowlists derived from them, modelled on the existing `_LEDGER_FIELDS` allowlist in `kernel/src/kernel/token_usage.py`. The decision handler (`kernel/src/kernel/decision_telemetry.py`, `DecisionTelemetryHandler`) currently persists any mapping a publisher sends; it must drop unknown keys at write instead. Payload schemas are exported as JSON Schema and committed so non-Python hosts and readers can validate rows. Adding a field bumps `schema_version`; removing or retyping is a hard cutover with a new version.
- Reader compatibility: readers accept every version up to current; a row with no `schema_version` is version 0 (legacy), read best-effort, never rejected, and counted in a read note; a row newer than the reader understands is reported unreadable, not silently skipped.
- Call-level join keys: each model call gets a `call_id` minted when the request is built, unique within its turn; a call is identified by `(turn_id, iteration, attempt)` where `attempt` is one of `primary`, `stream_tool_fallback`, `truncation_continuation`, `retry`. Where keys land: thread entry `turn_input.calls[]` gains `call_id` and `attempt` alongside `iteration` and `ref`; token usage rows gain `call_id`, `iteration`, `request_ref`; `turn.decision` rows gain the `call_id` of the call whose output the decision resolved; `tool.telemetry` rows gain `dispatch_id`, `tool_call_id`, the requesting `call_id`, and `iteration`; off-turn `model.request` rows gain `call_id` and the `dispatch_id` of the operation that made the call; approval ledger rows gain `tool_call_id` and `dispatch_id`. `dispatch_id` is minted per tool or operation dispatch including rejected dispatches, so a rejection row and its transcript tool result address each other.
- Run provenance: the host builds one run manifest at startup and rebuilds it whenever packs, modes, policy, or router configuration reload; stored once in the result-object store and addressed as `run_ref` (`r<sha256>`). Manifest fields: `lisa` (installed versions of kernel, runtime, sdk, mcp_server), `packs[]` (name, version, content hash of each installed pack's tree), `config` (content hashes of resolved mode, policy, router configuration), `model_data_version`, `host` (host type and host protocol version), `python` (interpreter version). The manifest never contains filesystem paths, environment variables, or credentials. Thread entries gain `run_ref` and `mode_digest` (content hash of the resolved mode definition the turn actually ran, after overrides); every ledger row carries `run_ref` via the envelope.
- Lineage: every execution gets a `turn_id`; the kernel already mints one (`provenance.kernel_turn_id`) and this spec promotes it to a top-level thread entry field and an envelope field. Fork and delegate child turns (`kernel/src/kernel/turn_phases/_child_turn.py`) currently send tokens and status to the parent but record no identity of their own; they will mint their own `turn_id`, carry `parent_turn_id` and `parent_dispatch_id` (the fork or delegate dispatch that spawned them), and keep the parent's `turn_index` because they belong to the parent's thread turn. This yields a tree under each `turn_index`.
- Reader changes: `sdk/src/sdk/forensics/reader.py` (`ForensicReader`) and `sdk/src/sdk/forensics/render.py` (`render_bundle`) join token rows to calls by `call_id` and render per-call cost under each iteration, join dispatch rows to transcript tool calls by `tool_call_id`, render the delegation tree from `parent_turn_id`, name the run manifest per turn and flag when consecutive turns ran under different manifests, and report legacy and unreadable rows in read notes.
- Privacy: envelope and payload fields are identifiers, counts, hashes, statuses, and bounded reasons only — no prompt, response, or tool-argument content; allowlists are enforced at write so a publisher bug cannot leak content to disk; `run_ref` objects are host-wide and contain no user data.

**Non-goals to state:** no model response content (that is Spec 2); no OpenTelemetry work (this spec only reserves the `trace_id`/`span_id` slots).

**Acceptance gate (all six):** a schema test asserts every publisher's payload validates against its committed JSON Schema and that the decision handler drops unknown keys; a turn with a streaming tool-call fallback produces two `turn_input.calls` entries with distinct `call_id`s and `attempt` values and two token rows that join to them; a failed dispatch row joins to exactly one transcript tool result by `tool_call_id`; a delegate child's rows carry its own `turn_id`, the parent's `turn_index`, and `parent_dispatch_id` equal to the delegate dispatch's `dispatch_id`; reloading a pack changes `run_ref` and the next thread entry records the new one; legacy rows still render with a read note counting them.

**Open questions to carry forward unresolved:** whether `run_ref` objects live in the per-thread result store or a host-wide store under `<data-dir>` (host-wide avoids duplicating them across conversations), and how to version the approval ledger's existing rows without rewriting the file (default: treat them as version 0).

### Spec 2 — Model Call Archive (docs/SPEC/MODEL-CALL-ARCHIVE.md), Order 2 of 4, depends on Spec 1 (call_id, attempt), unblocks Spec 3

**Goal:** Every model call, in-turn or off-turn, has an archived request AND response pair addressed by `call_id`, sufficient to reproduce what the call did to the loop without contacting the provider. Today requests are archived (`TurnHooks.models.record_request` in `kernel/src/kernel/turn_hooks.py`, and `OperationHost._record_request_snapshot` in `kernel/src/kernel/seams/host_adapter.py` for off-turn calls) but responses are not — only the assistant message and tool calls appended to transcript, a token usage row, and the final `finish_reason` survive, and the read surface caps reasoning at 800 characters. Intermediate finish reasons, truncation flags, continuations, provider request IDs, streaming facts, and failed or cancelled calls leave no durable record.

**Concrete content:** add `record_response` next to `record_request` on `TurnHooks.models` with the same contract (accepts a snapshot, returns an `r<sha256>` ref, persists into the same result-object store in the same record shape, and a recording failure logs a WARNING while the call proceeds unrecorded). `OperationHost` records off-turn responses through the same hook on its audit context. Response snapshot fields: `call_id`, `attempt`, `iteration`, `request_ref`, `outcome` (`ok`, `error`, `cancelled`, `wall_budget_expired`, `stream_idle_timeout`), `content`, `tool_calls`, `reasoning_content` (verbatim and uncapped from `CompletionResult` in `kernel/src/kernel/provider_contracts.py`), `finish_reason`, `truncated`, `continuation`, `provider`, `model_id`, `provider_request_id`, `usage` (same "unknown is not zero" rules as the token ledger), `duration_ms`, `streamed`, `time_to_first_token_ms`, `chunk_count` (null when not streamed), and `error` (exception class and a bounded message for non-ok outcomes; never a traceback or headers). Non-ok calls are recorded too. Raw provider payloads are archived only with explicit operator opt-in, off by default. Refs land as: thread entry `turn_input.calls[]` becomes `{call_id, iteration, attempt, ref, response_ref}`; the `model.request` ledger row gains `response_ref`; the token usage row is unchanged and joins by `call_id`. The thread store spec's `turn_input` row must be updated when this lands. Read surfaces: read-time redaction (`sdk/src/sdk/thread/redaction.py` `resolve_redaction_policy`) applies to response objects exactly as to request objects; `/forensics` and `turn_forensics` show one line per call (model, attempt, outcome, finish reason, time to first token, duration, tokens, cost) with content behind the ref; full `reasoning_content` is readable only through the existing `include_raw` bypass and the 800-character cap stays the default; a call with a ref but no `response_ref` is reported as an archive gap in read notes so loss stays countable. Note the storage duty: measure response-archive growth on a live store before landing and record the figure in the spec.

**Acceptance gate:** streamed turn with a tool-call fallback archives two pairs and the fallback's attempt is `stream_tool_fallback`; a truncation rescue archives the truncated response (`truncated: true`) and the continuation as separate pairs; a wall-budget expiry archives a pair with outcome `wall_budget_expired` and no content; a memory-mining operation archives a pair and its `model.request` row carries `response_ref`; a failing `record_response` logs a WARNING, the turn completes, and the forensic reader reports the archive gap; redaction tests cover response objects.

**Open questions:** per-chunk streaming timing versus only time-to-first-token and chunk count; whether tool results gain a parallel snapshot (current lean is no, because the transcript already holds results verbatim and `tool.telemetry` holds timing).

### Spec 3 — Turn Replay (docs/SPEC/TURN-REPLAY.md), Order 3 of 4, depends on Specs 1 and 2

**Goal:** Re-run any recorded turn through production code with the model answered from the archive, detect where a re-run diverges, branch a recorded turn into a live counterfactual, and export any turn as a permanent regression scenario. Define the vocabulary precisely: replay re-executes recorded work; rehydration (`runtime/src/runtime/thread/_rehydrate.py`) rebuilds the open task as model history and does not re-execute tools or model calls; a reprint is `/last`; continuing a paused task is a resume.

**Concrete content:**

- **Foundation:** `e2etest/src/e2etest/scripted.py` `ScriptedGatewayProvider` already replaces every provider gateway with a deterministic responder and runs everything beneath the model as production code. Replay is a scripted gateway whose script is the archive. The archive-backed gateway and the scripted gateway must share one implementation: move the gateway core out of e2etest into a runtime test seam and have e2etest import it, rather than maintaining two copies.
- **Three modes:** exact (archived responses in `call_id` order, recorded tool results; proves the loop reproduces the recording and finds behavior drift), counterfactual (archived up to a branch point then live, recorded tool results until the branch then policy-governed live), export (archived model and recorded tools, writes a regression scenario). Tools are never re-executed by default — each dispatch is answered from the recorded transcript result for its `tool_call_id` and write/execute effects are never repeated against the real workspace; `--live-tools=read` re-executes read-effect tools inside a scratch copy of the workspace; in counterfactual mode tools after the branch point run live under normal policy and approvals in a scratch data root and workspace. Recorded approval decisions from `approvals.jsonl` answer approval requests by `request_id` and `tool_call_id`, and an approval request with no recorded decision is a divergence, not a prompt to the operator.
- **Context pinning:** pinned (default for exact) serves each call's request from its archived snapshot so only the loop's decisions are under test; rebuilt re-assembles requests from current state and compares with the archive, and the first difference is the context-drift report.
- **Divergence detection:** at each model call compare model ID and sampling parameters, the tool list (names and schema hashes), and the messages by index and content hash; at each loop decision compare action and reason with the archived `turn.decision` row; the first mismatch stops the replay (or with `--continue` is reported and skipped) and the report names the call or decision, the field, and both values' hashes, with content diffs behind the same redaction rules as forensics. Before starting, compare the recorded `run_ref` with the current run manifest and list the packs, versions, and config hashes that differ — a divergence with a manifest change is expected, a divergence without one is a determinism bug.
- **Isolation:** replay runs in a scratch data root and never appends to the source thread or source ledgers; its own thread and ledger rows carry `replay_of: <turn_id>` and the replay mode so they are never mistaken for production evidence; wall-clock budgets are disabled in exact mode and recorded call durations are reported, not re-enacted; network access for model calls is disabled in exact and export modes and any call the archive cannot answer is a divergence.
- **Scenario export:** export writes a scenario under a pack's `tests/e2e/` containing a `.scenario.yml` declaring `model: {script: ...}`, a generated script module serving archived responses by call order, and assertions derived from the recording (effect receipts, `block_origin`, handoffs and transitions, yields, and the final answer's hash). The exported scenario runs under `lisa-e2e run <path>` like any other, so any production incident becomes a permanent regression test in one command. Export applies the redaction policy to the archived content it writes, and content the policy cannot clear blocks the export with an error that names it.
- **Surfaces and ownership:** `lisa replay <turn> [--mode exact|counterfactual|export]` operator CLI, and `/replay <turn>` in-session (exact only, report rendered like `/forensics`). The replay engine lives in `runtime` (`runtime.replay`) because it drives a real runtime. There is no model-facing operation in this spec.

**Acceptance gate:** every existing e2e scenario recorded once and replayed with exact has no divergence (this is the determinism gate and it runs in CI); a recorded production turn replays with identical effect receipts, `block_origin`, and lifecycle decisions; changing a mode prompt and replaying in rebuilt mode reports the first differing message and names the changed config hash; an exported scenario passes under `lisa-e2e run`; a replay never writes to the source data root, with a test asserting the source files are byte-identical before and after.

**Open questions:** sources of non-determinism inside the loop (UUIDs, timestamps in prompts, set ordering) which the determinism gate will find, each fixed by injection or recorded input; child turns (current lean is full child replay in exact via `parent_dispatch_id`, and a recorded result in export); turns recorded before Spec 2 existed have no responses and can only be replayed by lossy reconstruction from the transcript — the default is to refuse.

### Spec 4 — Trace Export and Timeline (docs/SPEC/TRACE-EXPORT-AND-TIMELINE.md), Order 4 of 4, depends on Spec 1 (turn_id, lineage, reserved trace_id/span_id)

This spec can start in parallel with Specs 2 and 3 because it only needs the envelope, but its call detail in the timeline uses Spec 2's archived pairs. It owns ledger and object retention policy and the export surface, and it fills the `trace_id`/`span_id` slots that Spec 1 reserves. This section is kept shorter than the others because it is the last slice and its design will be refined once Specs 1–3 land.
