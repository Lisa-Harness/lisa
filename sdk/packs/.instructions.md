# SDK Packs

Inherits all rules in `.github/instructions/python-development.md` and
`.github/instructions/code-quality.md`. The rules below are additive and
specific to `sdk/packs/`.

## Pack isolation

- Each pack is self-contained.
- A pack may import from `kernel` and `sdk` but must not import from
  `hosts/` or host runtime modules.
- Cross-pack imports should be avoided. If shared helpers are needed, promote
  them to `sdk`.

## Entry points and discovery

- Entry-point loading must remain side-effect-free on import.
- Registration/discovery happens via `pyproject.toml` entry-point groups.
- API keys and credentials are injected by host/runtime settings adapters, not
  read ad hoc from environment variables in arbitrary modules.

## Content-first where applicable

- Packs are primarily Markdown (`.operation.md`, `.mode.md`) and YAML
  (`.yml` metadata) when authoring mode/operation content.
- Python in content packs should be limited to response-format Pydantic models
  and thin runtime operation handlers.
- A runtime operation handler (`execution_kind="runtime"`) must be a single
  callable that accepts an `OperationExecutionContext` and returns an
  `OperationResult`. No framework logic, no routing, no state management.

## Telemetry/integration packs

- Packs that contribute signal connectors, digest sections, or context evidence
  may include integration modules (for example clients/connectors/models), but
  should remain deterministic and host-neutral by default.
- Keep integration pack runtime logic thin and testable; avoid embedding
  framework orchestration concerns.

## Operation authoring

- Each `operation_id` appears only once across all roots. Markdown operations
  take precedence over Python when both exist for the same id.
- Operations must be discoverable without side effects on import.
- Follow `docs/PACK_AUTHORING_GUIDE.md` for mode and operation file structure.
